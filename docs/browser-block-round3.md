# Browser block performance round 3

This continues [round 2](browser-block-round2.md) for Issue #184. The selected
direct tier follows forward conditional fallthroughs and loads only registers
used by a trace. It is now enabled in the normal browser build. It retains the
16-operation translation bound, original guest clocks, event deadlines, conventional-RAM checks and interpreter/guarded fallback.
The implementation is commit `894e2f2`; measurements use frozen Wasm and compiler
files rather than a changing checkout.

All controls below use three repetitions. The progressing comparisons are
separate alternating paired experiments, which explains their slightly different
candidate medians.

Every pair matched CPU/timing, conventional RAM, frame and PCM at all checkpoints.
The progressing direct tier covers 76.74% of measured instructions and averages
3.41 instructions per completion, versus 2.84 previously. It needs 26,707,703
direct completions instead of 31,850,431 for the same measured work.

Fresh NP2kai runs took 1,478.9 / 1,464.2 / 1,486.7 ms for 24.014471442 guest
seconds. The guest-time-normalized stationary host-time ratio is **2.26×** for
the selected tier, **2.34×** for round 2 and 3.45× for production. This remains
the scoped throughput comparison described under reproduction below.

The progressing and stationary controls now exceed the proposed 30% threshold,
and cold setup improves. **Enable the selected tier in the normal browser.**
Generated modules total 4,747,747 bytes in the progressing control, 41.42% above
round 2 and about four times production; this total is not a resident-memory
measurement. The existing 4,096-module limit remains. The shipped core adds
12,027 bytes over frozen production. The smaller 16-operation configuration and
sparse loads limit code growth; profile-guided path selection and further code
volume reduction remain useful next targets.

`web/block-jit.js` and `web/block-compiler.js` are canonical local assets; the old
tool entry points re-export them. The normal build enables the historical
`block-experiment` Cargo feature. The Worker first creates the guarded owner,
then selects the direct owner when its Wasm exports and module are available.
A missing direct module retains guarded execution; a missing base JIT or a
compilation failure retains the interpreter. `?jit=0` still avoids both modules.
Diagnostics retain `mode: "jit"` and add `tier: "ram-block"` and direct counters.
The normal publication audit now checks 30 assets and the direct exports.

A had exactly the previous experiment's direct instruction/call counters and
generated byte count in this game. Its new opcode family passed boundary tests,

bytes by 144,074 without changing those counters; it is retained for code size,
without claiming a separately established speedup. C alone added little useful
work. D's shared generated overlap helper passed code/gap/crossing-word tests,
but changed no direct counters and increased generated bytes, so it was removed.
E reduced run boundaries but generated 5,194,448 bytes. F generated 4,747,747 bytes
and had the better exploratory time, so the smaller configuration was selected.

## Execution contract

Only the uncached, ordinary 16-bit direct tier may follow the fallthrough of a
forward Jcc or LOOP-family branch. Backward branches retain their loop boundary;
unusual descriptors and guarded offers keep the previous collector contract.
The decoded path still stops at unsupported instructions, repeated targets and
16 operations. No native host assembly or browser-specific instruction extension
is introduced.

Generated code commits the branch's actual next IP, timing, count and register
changes, then checks that IP against the next decoded operation. A taken branch
exits before any fallthrough instruction or RAM store. The same successor check
preserves the existing changed-return behavior. Every instruction retains work
and event checks; all code spans are validated at admission, and stores retain the
conservative whole-hull self-code guard. There are no speculative bus effects to
replay.

Register use includes byte aliases, address bases/indices, dynamic write-mask
snapshots and every potentially dirty register. Even a future full-word write
requires loading that register's entry value: an earlier work/event/guard exit can
flush before the write. Never-used, never-written registers remain in CPU memory.
This removes unnecessary loads without changing partial-exit semantics.

The [original source comparison](browser-block-core.md#sources-and-architectural-choices)
still motivates keeping CPU execution inside an event budget and avoiding per-unit
host crossings. This iteration tests guarded path extension in our existing Wasm
translator; it does not copy another emulator's instruction implementation.

## Reproduction

The frozen production control remains commit
`62315e2c41f294f3eceafad478c9d24368c58f4f`. The previous experiment is main
`be0a5d28ee7bc554df6c40b77005931a1e36928d`, using the exact final round 2 Wasm
and its two runtime modules. Preserve both runtime files when comparing old and
new experiments; the paired command and `--baselineBlock`/`--baselineRuntime`
options in round 2 apply unchanged.
For a new snapshot, freeze the two `tools/lib/block-*.mjs` compatibility files
and the two canonical `web/block-*.js` files in the same runtime directory.
The measurement tools recognize both that format and older standalone modules;
an explicit snapshot never falls back to changing canonical files in the checkout.

Build the candidate with `--features block-experiment`, the normal SIMD release
flags and pinned Binaryen `-O3 -g`. The selected executable is 586,714 bytes; a
fresh final-source rebuild is byte-identical to the measured artifact. Runtime
assets are loaded into allowlisted servers before each browser starts. Private
HDD copies, raw guest state, code, PCM, captures and disassembly remain outside Git.

The host remains Apple M4 Max / ARM64 / Chrome 157.0.8103.52. Benchmarks run
sequentially, outside CPU-heavy validation. Progressing controls alternate engines
per scheduler slice and check equality at setup and 8/16/24 guest seconds. The
stationary controls use fresh browser processes and include software raster cost;
cold setup includes asynchronous compilation waits. NP2kai uses the same pinned
portable Wasm revision, scene anchor, 48 kHz audio and hardware configuration as
round 2. Its different CPU/timing/render model limits the ratio to guest throughput,
not equal retired-instruction efficiency or live playback quality.

## Validation

Local checks passed: 643 native tests with debug/overflow checks retained,
all-target/all-feature Clippy, formatting, 26 optimized-Wasm tests, 56 default
Node tests, 57 legal-fixture/check commands and the 30-asset publication audit.
The new native regression distinguishes direct fallthrough collection from an
unusual-descriptor guarded offer. The added Wasm controls cover sparse-register
partial exits, both forward branch outcomes with several work limits, and a RAM
store that must remain unexecuted on the taken path. Existing broad condition,
LOOP, flags, event, stack, self-code, memory-growth and return checks remain intact.

During exploration, a 32-operation assertion was accidentally run against the
older 16-operation artifact; the matching 32-operation build passed all 26 tests.
An exact-store guard fixture initially addressed two gap bytes rather than a
gap/code boundary; correcting its address exercised the intended rejection.
The final selected suite passes without either experimental feature. No existing
production assertion, skip or timeout was weakened.

Local Chrome additionally passed four production JIT/asset/fallback checks, with
two deliberate Pages skips for failure paths already checked at the local root.
The direct path executes at both serving roots and matches the interpreter's
clocks, registers, pixels and PCM. Both serial ADV98 playback cases passed at
48 kHz with the default owner and 44.1 kHz with the explicit interpreter, without
missed samples. The complete enabled application acceptance is recorded in the PR.

One stationary production launch failed before guest execution while the tool
compatibility modules were being relocated: the old server manifest lacked the
new canonical imports. Its log was retained and no timing sample was written.
After updating the manifest, the remaining controls ran with explicit frozen
runtime files. The temporary local Playwright configuration also needed an
explicit repository working directory; its initial server launch ran no tests.
Both corrected controls passed. Required post-merge verification is None.
Broader playback Issues #172/#146 remain separate.
