# Browser block performance round 5

This continues [round 4](browser-block-round4.md) for Issue #189. The selected
configuration adds a preflighted byte-OUT path inside the Wasm core and moves a
frequent read-only keyboard query ahead of the general BIOS switches. It keeps
the browser runtime, direct compiler, guest clocks and device boundaries.

## Repeated results

Three repetitions per retained control give the following medians:

| Control | Frozen main | Selected | Host-time reduction |
| --- | ---: | ---: | ---: |
| Progressing scene, active work | 3,556.0 ms | 3,439.5 ms | **3.28%** |
| Stationary scene, CPU and software raster | 3,165.3 ms | 3,021.9 ms | **4.53%** |
| Stationary cold setup | 28,200.2 ms | 28,143.6 ms | **0.20%** |

Every progressing pair improved, by 2.92–3.28%. The table reports reduction of
medians, not confidence intervals. Cold setup differs by only 56.6 ms; no
substantial startup improvement is established.

Fresh NP2kai runs have a median of 1,482.9 ms for 24.014471442 guest seconds.
Normalizing by guest seconds, the stationary host-time ratio falls from
**2.14× to 2.04×**. This remains a substantial gap. These are fresh same-session
ratios; they are not formed from historical samples.

All progressing pairs match CPU/timing, conventional RAM, frame and PCM at setup
and 8/16/24 guest seconds. Each measured window advances 24.0002795 guest seconds.
Generated code remains 3,437 modules totaling 4,747,747 bytes, with 91,056,703
measured direct instructions in 26,707,703 completions. Translated coverage does
not increase. Generated byte totals are not resident-memory measurements.

The [sanitized results](browser-block-round5-results.json) contain samples,
artifact identities and resource counts. Private media, guest state, code,
profiles, PCM and captures remain outside Git. The older production control stays
frozen for historical comparisons; this round's repeated progressing control is
the default round 4 runtime.

## Diagnosis and configurations

A separate instrumented build counted 5,509,321 entries into the standard F000
BIOS thunks during the progressing window. Of these, 5,506,790 (99.954%) were
INT 18h/AH=04h keyboard-group queries. This count excludes the separate LIO trap
family. Diagnostic timings are not used as performance evidence, and the selected
build contains no counters or diagnostic exports.

| Configuration | Change | Exploratory reduction against frozen main | Decision |
| --- | --- | ---: | --- |
| A | Install direct-completion timing state once | -1.11% | Remove; slower despite equivalent state |
| B | Core byte-OUT path with proven keyboard-service admission | 2.62% | Retain |
| C | B plus early dispatch of the read-only keyboard-group query | 3.20% | Select for repeated controls |
| D | C plus a three-unit preflighted native chain after hot INT | 3.17% | Remove; no clear additional benefit |
| E | C plus early ordinary RAM/ROM bus decoding | 3.22% | Remove; no clear additional benefit |
| F | C with separate compile-time INT/IRET and OUT instantiations | 2.55% | Remove; larger code without a speed benefit |

These single-run screens select a configuration, rather than isolate causal
speedups. B and C are retained as a small combination; the held-out repetitions
above assess that combination. D changed discovery and generated-code counts,
but reduced direct completions by less than 0.01%. F grew the core by 2,432 bytes
relative to C. Rejected sources and raw logs are external; none of A/D/E/F remains
in the final runtime.

The [source comparison](browser-block-core.md#sources-and-architectural-choices)
continues to motivate reducing general dispatch and state-copy costs in an event
budget. This iteration uses shared CPU, bus and firmware helpers; it copies no
upstream instruction implementation, patches no guest program and introduces no
native executable-memory JIT or new browser instruction requirement.

## Execution contract

Warmed unsupported probes may hint at byte OUT (E6/EE), in addition to the existing
INT/IRET families. A hint never replaces current-byte or state validation. Code
must be a complete, ordinary-RAM or ROM span, in Ap real mode without paging,
TF, an interrupt shadow, halt/shutdown, pending REP continuation or firmware
request. Pending IRQs return to the complete reference step before delivery.
Prefixes and mapped or faulting fetches retain the reference path.

Ordinary byte OUT cannot raise an architectural I/O privilege fault in this
admitted real-mode state. It uses the original fetch and output-width helpers,
including bus timing, port/device effects and synchronization. Port F0 can request
synthetic firmware and remains excluded unless the current selector/next-IP and
AH identify the existing real-mode keyboard services 00h..05h. Those services
use only registers, the keyboard queue and low RAM; without paging their original
preflight and body cannot fault. All other firmware requests retain the restart
checkpoint and error handling. No firmware service is reimplemented or skipped.

The original firmware transaction still consumes its request, marks approximate
timing, synchronizes devices before and after the service, and flushes the timing
cache. Actual register changes determine the timing dependency mask. Every unit
advances the original rational clock converter and ticks the bus. Discovery keeps
its existing one-unit hot boundary and two-unit ROM pair; a longer chain was
rejected. INT/IRET frame validation and stack/return behavior remain unchanged.
Observer/reference CPU APIs retain full stepping.

The shared BIOS dispatcher handles AH=04h after the existing mode/trap-location
validation, before the general preflight and service switches. That query has no
output preflight. It retains the same memory read/translation, so VM86 paging,
permissions, access bits and faults still apply. Invalid group numbers return
zero without a read. This shared dispatch change also applies to interpreter
execution; it does not change the query's semantics.

## Reproduction and limits

Freeze main `20daff0be28f50fd82a8fc1ef159b795a45e27fe`, its optimized core and
runtime modules. Its core is 585,863 bytes, SHA-256
`19d1c7db616fae39d74dbf20ed13326e8205620e467598d901e406bc452d5670`.
The older production control remains `62315e2c41f294f3eceafad478c9d24368c58f4f`.

Build the selected core with normal SIMD release flags, `block-experiment` and
pinned Binaryen `-O3 -g`. The selected core is 587,813 bytes, SHA-256
`b1cd154727d229e559aaf6d101d2162887425b2a09d0e48a578f7a83210c53a1`.
This adds 1,950 bytes (0.33%) over main. Freeze the two tool compatibility wrappers,
the two canonical `web/block-*.js` modules and `web/jit.js`; selected JS bytes are
identical to main. The round 4 commands and explicit frozen-runtime options apply
unchanged to `tools/measure_ram_blocks.mjs --repeat=3`.

Progressing active time excludes asynchronous compilation waits and checkpoint
hashing. Its setup-active measurement is not cold wall time. Fresh stationary
processes use `tools/measure_browser_bell.mjs --block=1`, alternating three runs
per core with three pinned NP2kai runs. Stationary active time includes CPU and
software raster work. Cold setup includes module/media acquisition, machine and
guest setup and compilation waits, excluding browser launch and initial JS
imports. All performance controls run sequentially on Apple M4 Max / ARM64 /
Chrome 157.0.8103.52 without CPU-heavy validation alongside them.

The reference remains portable Wasm NP2kai revision
`5939e0c6d5985c4c08fc70f289a83290e5d3e6f7`, Emscripten 6.0.13-git, i486DX at
65,894,400 Hz, 4 MiB, 86 sound and 48 kHz. It uses the same private media and
stationary scene anchor as earlier rounds. Our Ap DX2 uses 66 MHz and its existing
clock model. The normalized ratio is scoped guest throughput, with different
CPU/timing/render models; it is not equal-instruction efficiency or live playback
parity. NP2kai cold setup is not instrumented by this harness.

## Validation

Local checks passed: 649 native tests with debug/overflow checks retained,
all-target/all-feature Clippy, formatting, 30 optimized-Wasm tests, 56 Node tests,
56 legal-fixture/check commands, 13 offline fixture-fetch tests and the 30-asset
publication audit. The final normal-build Wasm is byte-identical to the measured
selected artifact.

Local Chrome passed four default JIT/asset/fallback checks at both serving roots,
with the two existing intentional Pages skips for failure paths covered once at
the local root. A separate unprofiled sound-enabled normal-timer game smoke ran
23.306 wall seconds and 23.300 guest seconds with the RAM owner. It produced and
consumed 1,118,413 samples, with zero underflows, overflows, drops, sequence errors,
checksum errors or emulator errors, and performed 105 HDD reads. This single smoke
checks adoption, rather than fixed-work speed or broad playback parity. Serial
ADV98 playback and complete enabled application acceptance are recorded in the PR
CI; they are not repeated as a separate local audio run in this iteration.

Native controls compare byte OUT and all six admitted keyboard services with
reference CPU stepping, including empty/populated queues, cached/uncached modes,
register upper halves, invalid-group boundaries and port effects. A subsequent
reference transaction checks retained timing/cache state. Unproven firmware,
prefixes, interrupt shadows, traps and a mapped immediate boundary must decline
before effects. The VM86 query test independently checks translated data, user
permissions, A-but-not-D bits, faulting reads and an invalid group with no page
walk. The added release-Wasm control warms actual keyboard polling and asserts
literal INT/OUT/IRET return positions, register values, flags and SP while varying
work/deadline limits and changing RAM groups. Existing assertions, timeouts and
intentional skips are preserved.

A new exploratory bus fixture initially assumed Ap-sized backing RAM for the V30
profile and failed before exercising the candidate. Initializing extended backing
only for Ap fixed the fixture while retaining both profiles' literal alias,
window and rollback assertions. The corrected native suite and release-Wasm
controls passed; the bus optimization was subsequently rejected for its result.
Required post-merge verification is None. Broader #172/#146 remain separate.
