# Browser block performance round 4

[Round 5](browser-block-round5.md) continues with byte-OUT and BIOS polling costs.

This continues [round 3](browser-block-round3.md) for Issue #187. The selected
change shortens word transfers and adds a preflighted INT/IRET fallback inside
the Rust core. That core is compiled to Wasm for the existing browser Worker.
The direct translator, translation limit, guest clock model and default browser
selection stay the same.

## Measured outcome

Three repetitions per retained control give the following medians:

| Control | Frozen main | Selected | Host-time reduction |
| --- | ---: | ---: | ---: |
| Progressing scene, active work | 4,095.4 ms | 3,895.3 ms | **4.89%** |
| Stationary scene, CPU and software raster | 3,349.5 ms | 3,126.2 ms | **6.67%** |
| Stationary cold setup | 28,974.5 ms | 29,187.2 ms | **-0.73%** |

Every progressing pair improved, by 4.45–4.89%. The table reports reduction of
medians; those are not confidence intervals. Cold setup increased by 212.7 ms,
so no startup improvement is established. The shipped core is 585,863 bytes,
851 bytes smaller than main. Generated code volume is unchanged.

Fresh pinned NP2kai runs have a median of 1,442.6 ms for 24.014471442 guest
seconds. Normalizing each engine by guest seconds, the stationary host-time ratio
falls from **2.32× to 2.17×**. This is closer to the reference but leaves a
substantial gap. It is a fresh same-session comparison, not a ratio formed from
historical samples.

All three progressing comparisons matched CPU/timing, conventional RAM, frame
and PCM at setup and 8/16/24 guest seconds. Each measured window advances
24.0002795 guest seconds. Generated modules remain 3,437 and total 4,747,747 bytes;
the measured direct work remains 91,056,703 instructions in 26,707,703 completions.
The gain comes from fallback work rather than increased translated coverage.
Generated byte totals do not measure resident memory.

The [sanitized results](browser-block-round4-results.json) contain the individual
samples, executable/runtime identities and resource counts. Raw guest state,
code, media, PCM, profiles and captures remain outside Git. The old production
control remains frozen for historical comparison; this iteration's repeated
progressing control is the default round 3 runtime.

## Diagnosis and candidates

A separate instrumented build counted 27,606,626 fallback units in the progressing
window. INT, OUT and IRET account for approximately 61.6% of these units. A fallback
unit is not necessarily a retired macro instruction, particularly for REP.
Instrumentation is excluded from performance comparisons and the selected build.

| Candidate | Change | Exploratory time reduction against frozen main | Decision |
| --- | --- | ---: | --- |
| A | Cache merged physical code spans and hull bounds | 0.42% | Remove; too little benefit for added state |
| B | Hint a three-unit interpreter burst at hot INT boundaries | 0.80% | Remove; little benefit and additional probing rules |
| C | Reuse word bus helpers for interrupt vectors and real frames | 1.18% | Retain as part of the selected configuration |
| D | C plus unpaged word-operand bus fast paths | 1.46% | Retain as part of the selected configuration |
| E | D plus coalesced RAM word timing | 1.53% | Remove timing specialization; no clear incremental benefit |
| F | D plus smaller restart checkpoint for INT/IRET | 0.16% | Remove; guards offset the saved copy |
| G | D plus forced entry-helper inlining | -8.72% | Remove; worse code layout/performance |
| H | D plus generated loops for a backward internal suffix | 1.21% | Remove; little useful boundary reduction and larger generated code |
| I | D plus core-resident preflighted INT/IRET fallback | 4.62% | Select for independent repeated controls |

These are one-run selection screens, not isolated causal estimates. In particular,
C and D alone do not establish separately repeatable speedups. Host load and code
layout vary; use the paired repeated controls above for the retained combination.
H reduced measured direct completions by only 0.34% and increased generated bytes.
No rejected configuration remains in the final runtime.

The [source comparison](browser-block-core.md#sources-and-architectural-choices)
continues to motivate an ordinary-RAM fast path and execution inside the core's
event budget. This iteration implements those principles in the existing shared
bus and CPU helpers. It copies no upstream instruction implementation and adds no
native executable-memory JIT or browser-specific instruction extension.

## Execution contract

Complete access validation still precedes word operands. Unpaged two-byte operands
can then use the existing word bus helpers, which preserve the two byte timing
accesses, write journal and device/boundary fallback. V30 operands that wrap their
16-bit segment offset retain the byte path. Paging retains translation, access
bits, permission checks and fault rollback. Interrupt vectors use two word reads;
contiguous real-mode frames use three word transfers in the original order.

Only a warmed unsupported probe hints that a core INT/IRET specialization might
be useful. Every unit rechecks the current opcode, CPU mode, code span, complete
frame, vector bounds and pending interrupts. Changing code or a vector never
reuses a decoded interrupt transaction. The existing two-unit synthetic-ROM burst
can specialize its IRET after executing OUT through the original firmware path.
Cold discovery and supported trace admission retain their previous behavior.

The specialization requires Ap real mode without paging, TF, an interrupt shadow,
halt/shutdown, pending REP continuation or firmware request. Code is ordinary RAM
or the synthetic ROM; INT's immediate and complete vector and stack transactions
must be ordinary RAM. Wrapped, big, mapped or faulting spans decline before any
fetch or bus effect. Pending IRQs return to the reference step before delivery.
The no-IRQ path preserves cascade synchronization.

After preflight, existing opcode fetch, interrupt delivery, IRET and timing helpers
perform the transaction. This avoids the general restart checkpoint and opcode
dispatch only where no instruction fault is possible. Each unit still advances
the rational clock converter and ticks the bus, checking work/event limits before
the next unit. Observer/reference APIs retain the complete interpreter step.
The generated-code admission, self-code guards, guarded tier and interpreter
fallback remain available.

## Reproduction and limits

Freeze main `a9240c41ca40b34152652f691df1c9031b08c90b`, its optimized core and its
runtime files before measuring. The core is 586,714 bytes with SHA-256
`eb09b060d98bbb58b390d9a3513a7b4cab76013cf04938aa7a8626c753ed5785`.
The frozen older production control is `62315e2c41f294f3eceafad478c9d24368c58f4f`.

Build the selected core with the normal SIMD release flags, `block-experiment`
and pinned Binaryen `-O3 -g`. Freeze the two `tools/lib/block-*.mjs` wrappers,
the two canonical `web/block-*.js` files and `web/jit.js` in the runtime directory.
The selected JS files are identical to main. The selected optimized core SHA-256
is `19d1c7db616fae39d74dbf20ed13326e8205620e467598d901e406bc452d5670`.
Use `tools/measure_ram_blocks.mjs`
with `--baselineBlock=1`, explicit `--baselineRuntime` and `--candidateRuntime`,
private absolute media/output paths and `--repeat=3`. The script alternates engines
per slice and excludes asynchronous compilation waits and checkpoint hashing from
active time; its setup-active measurement is not cold wall time.

Use `tools/measure_browser_bell.mjs --block=1 --blockRuntime=...` for three fresh
stationary runs per core, alternating their order with three fresh NP2kai runs.
Cold setup includes module/media acquisition, machine setup, emulated setup and
compilation waits; it excludes browser launch and the initial JS imports. The
stationary active window includes CPU and software raster work. Measurements run
sequentially on Apple M4 Max / ARM64 / Chrome 157.0.8103.52, without CPU-heavy
validation alongside them.

The NP2kai reference remains portable Wasm revision
`5939e0c6d5985c4c08fc70f289a83290e5d3e6f7`, Emscripten 6.0.13-git, i486DX at
65,894,400 Hz, 4 MiB and 86 sound at 48 kHz. The same private media and stationary
scene anchor are used. Our Ap DX2 model runs at 66 MHz with the existing timing
model. Different CPU/timing/render implementations make this a scoped guest-time
throughput ratio, not equal instruction efficiency or proof of live playback
quality. NP2kai cold setup is not instrumented by this harness.

## Validation

Local checks passed: 646 native tests with debug and overflow checks retained,
all-target/all-feature Clippy, formatting, 29 optimized-Wasm tests, 56 Node tests,
56 legal-fixture/check commands plus 13 offline fixture-fetch tests, and the
30-asset publication audit. The final normal-build Wasm is byte-identical to the
measured selected artifact. After Clippy's test-only initializer correction, the
focused native word test passed again.

Local Chrome passed four production JIT/asset/fallback checks, with the two
existing deliberate Pages skips for failure paths already checked at the local
root. Both serial ADV98 audio cases passed without missed samples: the default
owner at 48 kHz and the explicit interpreter at 44.1 kHz. After both cases had
completed, the local Node 26 Playwright worker hung during shutdown. Its verified
owned worker required termination; the coordinator then reported two passes and
exit zero. The complete enabled application acceptance is recorded in the PR.

A separate unprofiled normal-timer game smoke ran 23.329 wall seconds and
23.330 guest seconds with sound enabled and the default RAM owner. It produced
and consumed 1,119,853 samples, with zero underflows, overflows, drops, sequence
errors, checksum errors or emulator errors. It performed 105 HDD reads. This
single smoke checks adoption; it is not the fixed-work speed comparison or a
resolution of the broader playback investigations.

The independent per-byte native oracle covers offset wrap, hidden limits, A20,
mapped memory, timing and rollback. Native interrupt controls compare full CPU
state, RAM and timing with reference stepping, including cached/uncached modes,
odd stacks, relocated vectors, IF and incoming flag changes; excluded states
must decline without effects. Release-Wasm tests add literal interrupt frame and
V30 wrapping expectations, plus a warmed owner loop with varying work/deadline
limits and live vector/opcode changes. Existing assertions, skips and timeouts
are preserved.

During exploration, the longer INT burst initially violated the existing hot-ROM
pair work-count assertion; narrowing the hint restored the old ROM behavior. The
candidate was subsequently rejected for its measured result. The first local
Clippy check caught a default-field initializer style issue in the new test;
initializing that field directly fixed it without a runtime change. Raw logs
and rejected sources are external.
Owned Chrome occasionally needed the harness's bounded shutdown after complete
results had been written; these completed samples are retained. No timing from
the diagnostic build is used as performance evidence.

Required post-merge verification is None. Broader playback Issues #172/#146 remain
separate. The enabled normal runtime and its interpreter/guarded fallback remain
part of acceptance.
