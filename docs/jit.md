# Browser x86-to-WebAssembly JIT — Issues #150 and #152

With JIT selected, the browser emulator dynamically compiles hot Ap real-mode instruction blocks
into WebAssembly. Generated code implements register and memory operations, flags, word stack
operations and near calls/returns. It shares the owning core's memory and calls Rust at every instruction
boundary to preserve fetches, guest clocks and device events. The native core
and synchronous `step`/observer APIs retain the interpreter as their reference.

## Coverage and controls

The tier covers unprefixed 8/16-bit ALU, MOV, XCHG, TEST, NOT/NEG,
register INC/DEC, SAHF/LAHF, carry/direction flags, short conditional branches,
LOOP/JCXZ, relative JMP/CALL, word register PUSH/POP, near RET and single-bit
register shifts/rotations (`D0`/`D1`, including the SHL/SAL alias). Memory operands
use 16-bit ModR/M addressing or accumulator absolute offsets. Blocks contain at
most 16 instructions and stop at a branch or unsupported operation. Prefixes,
strings, memory/variable-count shifts, far transfers, other stack operations, I/O, firmware services,
protected/paged execution, 32-bit defaults, single-step and unusual fetch
boundaries use the existing interpreter. This is a bounded first tier, not a replacement for the
full CPU implementation.

Browser sessions enable the JIT by default. Add `?jit=0` (or `&jit=0`) for
interpreter comparisons or troubleshooting; explicit `?jit=1` remains supported.
VM uses the interpreter. An unavailable JIT
module or compilation failure also retains interpreter execution; no browser or
runtime dependency is downloaded. The compiler is the original MIT-licensed
[`web/jit.js`](../web/jit.js), using the standard
[Wasm binary format](https://webassembly.github.io/spec/core/binary/modules.html)
and asynchronous
[WebAssembly compilation](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/compile_static).

With `?diagnostics`, `pc98.stats().jit` reports the selected mode, compilation
offers/completions, cached modules, generated byte totals, compilation wall
latency, committed translated instructions, invalidations and failures. Wall
latency includes asynchronous scheduling; it is not compiler CPU time. Cache
and execution counters reset at reset/profile/HDD-replacement barriers, while
identity numbers remain monotonic so an old compilation cannot register itself
into a new machine generation.

## Boundaries preserved

The Rust bridge lives in [`src/cpu/jit.rs`](../src/cpu/jit.rs). It observes hot
addresses through a 16,384-entry heat table, offers blocks after 32 observed visits, and
bounds native plans and compiled modules to 4,096 entries. Only one compilation
is in flight. Evicted addresses can warm again. Compilation is asynchronous;
guest execution continues through the interpreter until a module is ready.
Cold code is sampled between short interpreter runs of 3–6 units, reducing
discovery overhead on memory-heavy code. Ready blocks can chain immediately.

Every block entry checks CPU mode, TF and CS base. Supported operations cannot
change mode, segment registers, TF, halt or REP state while the synchronous Wasm
dispatcher runs. Unsupported control changes leave the block and pass the full
entry guard again. Each instruction still checks the interrupt shadow, IRQs,
current CS bounds, expected IP and every code byte before its semantics run. Branch targets are checked against the current segment bounds,
including after a hidden-cache change. A conservative rejection returns to the
interpreter, which decides whether an untaken branch actually faults. Code
mutation stops the old block before the changed operation and allows rewarming.

With interrupts enabled, the bridge refreshes the PIC cascade wire even if no
vector is pending. A pending vector returns to the original interrupt delivery
path. Each committed operation retains the original instruction fetch bus
activity, timing table, register dependency mask and rational CPU/device clock
conversion. Devices tick after every instruction, including a zero-clock tick;
PCM/timer/IRQ work is never deferred to the end of a block. Both the 80,000-clock
deadline and the 100,000-unit cap remain effective inside compiled blocks.

A small Wasm dispatcher calls ready modules through a bounded function table,
avoiding a JavaScript round trip between short blocks. It returns at a compilation
offer or slice end. Entry distinguishes an offer from a stale plan invalidated by
its byte guard; stale entries fall back without resubmitting an old packet.

Memory address forms, widths and access directions are decoded once. Validated
physical operand addresses are reused within each instruction. Exact known GPR
change masks avoid whole-bank snapshots/comparisons for flag-only instructions
and operations that always change a specific word register; identity/alias cases
retain actual-change comparison. Each entry
computes the current offset and validates the complete operand against the current
hidden segment bounds. A two-word scratch area carries the bus-read value and
generated write result across the instruction boundary. Rust performs the original
byte bus accesses, retaining cache/wait accounting and video-device effects. Bus
writes commit before the next instruction's byte guard, including self-modifying
stores. Complete preflight avoids duplicate segment/paging checks during these
real-mode bus accesses; code fetches likewise keep each original bus access.
Word stack operations decline big stacks. RET target peeks are restricted to
ordinary RAM; mapped stacks or invalid targets return to the interpreter before
fetching/popping. Other mapped data operands retain the actual bus path.

Generated modules access the low register bank, FLAGS, IP and scratch area through
addresses obtained from the owning core, rather than assuming Rust field offsets. Cached
addresses are ordinary numbers, not typed-array views that detach when memory
grows. Byte and word writes retain neighboring bytes and upper register words.
Reset and media/control barriers run between finite slices and clear cache
ownership. The DOM and render Worker never own or execute guest blocks.

## Verification and measurements

`tests/jit.test.js` runs the actual release core and generated modules against
the interpreter, including arithmetic/flag boundaries, byte aliases, signed
immediates, every condition, LOOP, work/time caps, code mutation, IRQ/TF exits,
compilation failure, stale reset offers and upper words set by a 32-bit fallback.
The original boot programs in the tests use no proprietary game or ROM bytes.
Native bridge regressions cover unsupported/faulting fetches, mode/IRQ/shadow
guards, identity changes, PIC-wire history and changed branch bounds.

The actual production-Worker browser regression compares registers, clocks,
fetch counts, frame fingerprints and PCM fingerprints for default JIT, explicit
`jit=1` and explicit `jit=0` at both serving roots. A separate failure-path case
checks default-startup fallback for an unavailable JIT asset and verifies that
`jit=0` avoids loading it.
The existing legal guest and wall-clock audio suites remain required.

An opt-in original register-loop comparison needs no game media:

```sh
node tools/measure_jit.mjs --output=/tmp/pc98-jit-register.json --repeat=3
```

It warms 200,000 units on each fresh page, alternates mode order, then compares
5,000,000 units in installed Chrome. It checks registers, flags, IP, CPU/device
clocks, fetch/retirement counters and PCM fingerprints before reporting timings.
This is a supported-register workload, not a prediction for memory-heavy games.

The initial Issue #150 tier on Apple M4 Max, Darwin 27.2.0 arm64, Node 26.12.1 and installed Chrome
157.0.8103.38, three controls per mode measured:

| Register loop | Host ms, individual controls | Median host ms |
| --- | --- | ---: |
| Interpreter | 255.1, 282.9, 275.5 | 275.5 |
| JIT | 194.7, 217.7, 222.8 | 217.7 |

The median uses 21.0% less host time for the same work. Every compared state and
PCM fingerprint matches. Six blocks (3,601 generated bytes) warm on each JIT
page; their asynchronous compilation wall latency totals 8.4–9.2 ms. Timing
starts after warm-up; it does not include browser startup or initial compilation.

The initial Issue #150 installed-game comparison retains exactly 118,102,981 instructions,
1,584,018,440 CPU clocks, 131 reads, 1,464 music key edges, 934 sound IRQ edges,
1,152,013 PCM samples, PCM fingerprint 3,284,892,698 and final-frame fingerprint
1,013,578,406 in all modes. Per-instruction discovery initially made the JIT
screen about 5% slower. Sampling cold code removes that observed overhead in a
subsequent screen (8,056.1 ms versus the earlier 8,069.8 ms control), but these
are different builds and a single pair cannot establish a game speedup. The
repeated final comparison and pre-merge validation are recorded in
[Issue #150](https://github.com/takahirox/pc98-rust/issues/150) and its linked PR.
No visible-transition or audio-continuity improvement is inferred from the
register-loop result.

The final same-core comparison alternates mode order across six fresh Chrome
controls. Every canonical guest/PCM/frame result above matches:

| Installed-game mode | Host ms, individual controls | Median host ms |
| --- | --- | ---: |
| Interpreter | 8,080.3, 8,241.9, 8,203.3 | 8,203.3 |
| JIT | 8,273.8, 8,304.4, 8,297.3 | 8,297.3 |

Only 88,022 of 118,102,981 measured instructions used the initial tier (about 0.075%).
The initial JIT control was 1.1% slower by the median. Consequently the initial
release kept the interpreter as the browser default while coverage improved.
These historical explicit-mode measurements were collected at
`f606aac`; making that release opt-in changed neither the core/compiler bytes
nor either explicit-mode execution path. Normal-playback observations and final
acceptance are recorded in the linked Issue/PR.

The local installed-game harness supports `--jit=0` and `--jit=1`, freezes the
compiler asset alongside the runtime, and records JIT counters. Use one browser
at a time after builds/regression suites finish, without a debugger or profiler:

```sh
node tools/measure_doukyuusei2.mjs --media=/tmp/pc98-146/installed.hdi --output=/tmp/pc98-146/interpreter.json --channel=chrome --gameplay=1 --repeat=1 --jit=0 --yieldJit=1
node tools/measure_doukyuusei2.mjs --media=/tmp/pc98-146/installed.hdi --output=/tmp/pc98-146/jit.json --channel=chrome --gameplay=1 --repeat=1 --jit=1 --yieldJit=1
```

`--yieldJit=1` yields between 10 ms guest slices during setup and measurement,
allowing asynchronous compilation to progress as it does between production
Worker slices. Without it, a long synchronous inspection can hold compilation
until an entire eight-second guest window finishes and understate coverage.
`wallMs` sums active guest execution and PCM hashing; it excludes timer waits and
compiler tasks between slices. `spanMs` additionally includes these inter-slice
tasks and waits. `--yieldJit=setup` warms compilation during setup, then measures
continuous eight-guest-second windows with yields only between windows; this
separately controls the timer/host-scheduling spread seen with short slices. Neither measures visible transition completion or synthesis
quality. The CPU fingerprint covers the low register bank, FLAGS, IP and CS.

Alternate order and repeat; compare fixed work and guest results before comparing
host time. The [normal startup controller](doukyuusei2-reproduction.md) also
accepts `--jit=0|1`, defaults to the interpreter and records JIT activity.
Its image-change observations and delivery counters do not establish synthesis
fidelity. Game media, installed
HDDs, captures, recordings, raw profiles and raw reports stay outside checkout
and publication. Issue #146 remains open unless the original debugger-free
Chrome complaint is independently reproduced and resolved.


## Installed-game iteration — Issue #152

A separate aggregate opcode count on the canonical game window identified near
CALL and RET at about 7% each and register group TEST at about 4.7%. The initial
JIT did not cover these operations or the frequent memory MOV/ALU paths. A
synchronous inspection also prevented compilation from progressing during the
window; yielding increased old-tier coverage from 88,022 to 1,732,419 instructions,
while revealing 4,268 total compilations and a full 128-entry cache.

Exploratory candidates added memory/stack semantics, enlarged the bounded cache,
moved block dispatch into Wasm, combined operand accesses with existing boundary
callbacks, predecoded address forms and removed duplicate preflight checks.
Adding coverage alone made the game slower. Per-operand helper imports and
minimum-two-instruction admission were rejected. The selected candidate keeps
single-instruction blocks, a 4,096-entry cache and 3–6-unit discovery intervals;
it translated 72,662,313 of the canonical 118,102,981 measured instructions (61.5%)
in its initial screen. All canonical CPU/device clocks and PCM/frame fingerprints
matched. These screens select candidates; they are not the final repeated timing
claim. An intermediate nine-control short-slice comparison was 2.4% slower than
the previous JIT, requiring another iteration on preflight, register-change
bookkeeping and invariant entry checks.

The final alternating controls, artifact identities, elapsed-time definitions,
full validation and normal-playback observations are recorded in
[Issue #152](https://github.com/takahirox/pc98-rust/issues/152) and its linked PR.
Performance comparisons use the same harness and installed Chrome, with one
owned browser at a time and no concurrent local builds or test suites. The
reference interpreter remains available through `?jit=0`. Following these game
improvements, browser sessions now enable the JIT by default.

157.0.8103.38 host, nine fresh-browser controls used the balanced order
old/new/interpreter, new/interpreter/old, interpreter/old/new. Each used

Every control retains the canonical 24.0002795 guest seconds, instruction/clock,

## Further boundary experiments — Issue #156

The next investigation tested the researched techniques in separate, frozen-asset
controls rather than assuming that fewer operations would improve whole-game
capacity. The local original ADV98 scene/audio control passed both modes before
changes (32 windows, zero missing samples); the original normal-Chrome complaint
was not reproduced by that control. The prior CI scene-time failure in both
modes remains a separate observation in #146/#155.

All fixed-work comparisons use the same installed Chrome 157.0.8103.38 on Apple
M4 Max / Darwin 27.2.0, without concurrent owned builds, test suites or profilers.
Each three-mode experiment uses nine fresh browsers in the balanced order
A/B/C, B/C/A, C/A/B. Every mode validates the canonical instruction count,
CPU/device clocks, CPU/frame/PCM fingerprints, HDD reads and music/IRQ edges.
The harness additionally reports p50/p95/p99/maximum active execution time for
800 ten-guest-millisecond slices in each of its three windows. These timings
include PCM fingerprint work, not just CPU instruction execution. Profiled
controls are diagnostic evidence only and are excluded from timing comparisons.

Rejected prototypes are retained as numeric evidence, not extra runtime paths:

| Prototype | Same-round repeated result | Decision |
| --- | --- | --- |
| Defer OPN timer arithmetic until a flag event or register write | 7,874.1 ms median vs 7,905.2 ms baseline; 0.4% reduction within overlapping runs | Rejected: insufficient benefit for the extra scheduling state |
| OPN deferral plus unused FLAGS-load/local removal | 7,953.7 ms median vs 7,905.2 ms baseline | Rejected |
| Defer arithmetic FLAGS when immediately overwritten, restoring them on every boundary exit | 7,903.2 ms median vs 7,740.0 ms PIT-only control | Rejected: no incremental benefit despite exact results and exit/IRQ/self-modification tests |
| Reduced-unit, narrow CPU/device clock conversion plus PIT fast path | 7,759.3 ms median vs 7,780.4 ms baseline, but 7,780.2 ms mean vs 7,745.9 ms | Rejected: no repeatable benefit |
| Fixed-word instruction-byte guards added to that conversion | 8,141.4 ms median vs 7,780.4 ms baseline | Rejected: slower than the existing slice comparison |

The PIT mode-3 candidate avoids variable modulo while an advance remains inside
the active period; wrap handling, odd divisors, pending replacement divisors,
output/count values and IRQ edges retain their existing behavior. Existing
specification traces, single-clock/batch comparisons, zero/maximum advances and
reprogramming tests cover these boundaries. A separate nine-control comparison
measured 7,740.0 ms median (7,750.5 ms mean) vs 7,910.8 ms (7,888.7 ms).

A fresh baseline host profile identified interpreter fallback, JIT preparation,
bus ticking and timing retirement as the largest active contributors. The
existing same-game opcode aggregation also recorded about 2.53 million
unprefixed register `D0`/`D1` operations. The JIT extension covers their eight
single-bit shift/rotate groups with the existing CPU's precise flag policy;
rotates preserve SZP and all forms preserve AF. Register identity/alias cases
keep actual GPR-change comparison. Memory operands and other counts retain the
interpreter. Node regressions compare every byte value, both carries, all groups
and register aliases, word boundaries and randomized values against the actual
reference core. The existing production Worker probe now includes carry-dependent
SHR/RCL inside its call loop at both serving roots.


### Selected repeated comparison

The selected revision combines the register shift/rotate extension with the PIT
fast path and a 32-entry SSG amplitude table added to the existing constant
coefficient cache. The SSG table evaluates the original `powf` expression once
per level; sample multiplication order and every tone/noise/envelope update
remain unchanged. A new original synthetic register trace covers all 16 envelope
shapes and all 32 volume encodings, comparing PCM fingerprints captured from the
unchanged implementation. No game recordings or imported music are included.

Nine final continuous-capacity controls used the original main artifact and two
revised artifacts, with/without that SSG table. Other runtime assets and the
harness were identical; builds and tests were finished before the controls.

| Artifact | Active host ms, individual controls | Median ms | Mean ms |
| --- | --- | ---: | ---: |
| Main baseline | 7,887.8 / 7,885.9 / 7,845.5 | 7,885.9 | 7,873.1 |
| Selected JIT shifts + PIT + SSG table | 7,746.2 / 7,686.7 / 7,721.0 | 7,721.0 | 7,718.0 |
| JIT shifts + PIT, without SSG table | 7,814.0 / 7,736.1 / 7,904.3 | 7,814.0 | 7,818.1 |

The selected median is 2.1% lower than main, and its mean is 2.0% lower. All
three selected controls are below all three main controls. Each window's median
p99 active time per 10 guest milliseconds changes from 5.6 / 5.5 / 4.8 ms to
5.2 / 5.3 / 4.5 ms; observed maxima across these controls are 6.6 and 5.9 ms.
These are fixed-work capacity observations on this host, not a claim about
completed image-transition latency, other games or audio fidelity.

All nine controls retain 118,102,981 instructions, 1,584,018,440 CPU clocks,
24.0002795 guest seconds, 131 HDD reads, 1,464 music key edges, 934 sound IRQ
edges, 1,152,013 samples, PCM fingerprint 3,284,892,698, frame fingerprint
1,013,578,406 and CPU fingerprint 2,669,599,220. Continuous-window translated
instructions increase from 59,618,051 to 60,913,847. Compilation cannot progress
inside an eight-second synchronous window; production slices yield between

compiler SHA-256 is
`434d9923b16d1a3ba2ddf03404be826b56b9de190fadbff83fafbb35fb008afd`.

Separate normal visible Chrome controls use no debugger, CDP, profiler or

compilations with a full 4,096-entry cache, 13 valid invalidations and no failures.
These controls establish healthy playback and exercised eviction, not resolution
of the user's original symptom or physical synthesis accuracy.
